# VOLO-112 — Owned disposable database recovery rehearsal

Execute inline from merged VOLO-111 (`548f663`). Scope: document the supported logical backup/recovery path, perform one fictional local recovery, verify schema/data plus an app smoke, record Storage and beta limits. No hosted access/export/reset/restore or publication.

Method: reuse the existing real-Auth runner, owned local-stack helper, fictional seeds and compiled app fixture. Create distinct source/target stacks on the same pinned runtime. Rebuild target schema from the exact source migration revision; capture CLI roles/schema/data dumps and a migration/schema manifest. Require source/target schema/RLS/grants/functions/managed-schema hooks/history to match before data import. Restore data transactionally into the owned target with triggers suppressed only for that connection, then prove row hashes and critical constraints/authorization. Keep cron jobs inactive and deletion enablement false until reconciliation. This is migration-rebuild plus logical-data restore, not a physical/PITR or standalone schema-dump restore certification.

1. Add one `--recovery` group to the existing Auth verification runner, implemented in a recovery-case helper. Narrow all operations to generated, registered local project/container identities; use private temporary artifacts, no remote destination parameters, and clean up on failure/success, retaining private artifacts if cleanup fails and registering the target for `--cleanup --recovery`.
2. Use fictional seeds and real local Auth accounts for active/disabled members, PRIVATE flight, accepted request, conversation/message, participant outcome/report and a current photo. Capture source backup and metadata/data hashes; show the fresh target lacks the fixture, then restore that point even after a source-only change. Verify normal/disabled/unrelated access and actual compiled report/outcome/photo reads.
3. Show DB-restored photo metadata has no bytes on the fresh target. Restore the owned local Storage volume snapshot separately and compare downloaded bytes, MIME type and the actual photo HTTP response. Preserve file extended attributes through the installed Storage backend library; BusyBox tar and docker cp lose them. This local file-backend exercise does not certify a hosted S3/Storage recovery method. Record managed configuration, keys/encryption, sessions, scheduler/deletion reconciliation, backups/60-day retention and RPO/RTO limits as applicable.
4. Independently review the recovery boundaries/evidence, check targeted syntax/lint/doc links/diff, commit/push/create and attach PR. No repeated restore matrix, permanent environment, new recovery platform or production operations.
