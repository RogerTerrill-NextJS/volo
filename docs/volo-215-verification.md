# VOLO-215 — Audited flight moderation

Base: merged VOLO-214 (`76a2fe7`). This delivers VOLO-86's server-side step; VOLO-216 owns moderation controls and hidden-flight presentation.

`admin_hide_flight` requires current active-admin membership from the ordinary authenticated session. It rejects unauthorized callers before target locking, then rechecks and locks authority after taking the common flight lock. Actor, target, timestamp and reason are database-bound. Open posts use the existing cancellation operation; pending/accepted requests close, existing triggers close conversations, and subsequent acceptance, interest and sends are denied. Completed/cancelled posts retain their lifecycle status while any remaining active requests close. No profile or future-departure prerequisite prevents intervention.

The retained `moderated_at` marker cannot coexist with an open flight. Ordinary RLS retains the owner's post record but hides the post from other viewers, including selected PRIVATE recipients. Discovery already requires open status, so hidden posts disappear for every viewer. Request/conversation/message history retains its existing participant-only policies; unrelated administrators gain no message access. Terminal request rows and all post/recipient/history identities remain intact. No unhide, hard delete or new request/message state engine is introduced.

One immutable `flight_hidden` event per flight records moderator, target, time and required bounded reason in the same transaction. Audit failure rolls back post/request/conversation changes. Repeated or concurrent hides return the original timestamp without rewriting reason or adding audit events. Direct authenticated post/audit mutations and service-role RPC bypass are denied; the pre-existing privileged flight persistence grants are unchanged.

`admin_flight_overview` is an explicit, separate active-admin read of up to 51 UUID-ordered records, including PRIVATE/hidden posts. The server query validates the projection, returns at most 50 records plus a cursor, and rechecks current role/identity after reading. Only bounded flight/post/audit fields are returned, without Auth/email/contact data, recipient lists, request notes or private conversations. The action reuses existing origin/session/role/form-size guards, accepts only target/reason/confirmation, and returns exact-target confirmation or sanitized uncertainty without automatic mutation retries.
