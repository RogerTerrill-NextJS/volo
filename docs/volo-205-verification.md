# VOLO-205 — Message persistence and stable ordering

Based on merged VOLO-204 (`df2104d`). Messages belong to the existing accepted-request-only conversations. Each immutable row stores UUID, conversation UUID, sender UUID, plain-text body and server-managed created_at. The implementation default is 1–4,000 Unicode characters with at least one PostgreSQL non-whitespace character. Submitted spacing and markup-looking text are preserved as text; future views must escape it rather than render HTML.

The index `(conversation_id,created_at,id)` supports deterministic order and tuple-cursor paging. The persistence trigger assigns time after waiting for lifecycle locks and clamps it to conversation creation; caller-supplied timestamps are ignored. UPDATE is rejected even on privileged paths, keeping identity, body and ordering metadata immutable. Restrictive foreign keys prevent accidental conversation/member deletion from cascading through shared history.

Authenticated participants SELECT through the conversation's active-viewer RLS. Closed conversations and removed PRIVATE recipients retain authorized history without current flight visibility. An unrelated administrator has no bypass, and disabling the viewer revokes reads with the same identity. The service role has SELECT only; authenticated and service-role INSERT/UPDATE/DELETE grants remain closed. No send RPC, messaging UI, notification, receipt or Realtime publication is introduced before VOLO-81.

A persistence trigger additionally binds sender to auth.uid() and the immutable conversation pair; serializes on flight, request and conversation; holds both current active memberships; rejects closed_at and a missing accepted/open/current-PRIVATE connection. This protects even privileged fixture inserts and future guarded send wiring. The later VOLO-81 operation must continue deriving the sender from verified identity and respecting this lock order; these reads are not durable send grants.
