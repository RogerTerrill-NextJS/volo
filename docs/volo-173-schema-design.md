# VOLO-173 — Approved flight schema

Review proposal for [VOLO-173](https://outsidethecockpit.atlassian.net/browse/VOLO-173)
and its authoritative parent [VOLO-45](https://outsidethecockpit.atlassian.net/browse/VOLO-45).
The user requested starting this ticket after the local
[VOLO-172 visibility contract](volo-172-visibility-contract.md).
The user approved this schema design and the implementation plan in chat.
Implementation and local verification are recorded separately.

## Outcome and scope

Establish flight and selected-recipient persistence with safe initial read access,
database integrity constraints and generated Supabase types. Preserve current
membership authorization and NETWORK/PRIVATE visibility from VOLO-172. No UI,
posting endpoint, request/conversation tables, generic permission engine, hosted
Supabase changes or deployment belongs to this ticket.

## Approved fields

`flights`:

| Field | Definition |
| --- | --- |
| id | UUID primary key, generated by PostgreSQL |
| owner_id | Required membership foreign key, default authenticated identity; immutable after insertion |
| departure_airport, destination_airport | Required uppercase alphanumeric identifiers, 2–8 characters, matching profile airport format; same-airport flights allowed |
| departure_at | Required finite timestamptz, representing the UTC departure instant |
| departure_timezone | Required validated named IANA zone; UTC supported; reject arbitrary offsets and abbreviations |
| departure_local_date | Required date derived by the database from departure_at in departure_timezone; supplied values cannot create inconsistent date/time data |
| aircraft_description | Required nonblank trimmed text, maximum 500 characters |
| pilot_places | Required positive integer: joining-pilot capacity excluding the owner; no separately mutable remaining count |
| notes | Optional text, maximum 2,000 characters |
| visibility | Required NETWORK or PRIVATE, explicitly supplied |
| status | Required open/cancelled/completed, initially open, using the lifecycle vocabulary proposed in VOLO-13 |
| created_at, updated_at | Required server-managed timestamps |

`flight_recipients`: composite primary key `(flight_id, user_id)`, required
foreign keys to flights and memberships, and server-managed `added_at`.
The owner needs no recipient row. Reject duplicate-owner selection and selection
of a non-active member. Selection belongs to PRIVATE flights.

Use restrictive deletion foreign keys for identities and flight relationships;
do not cascade away shared history before retention rules exist. Omit moderation
fields until their owning ticket defines its guarded operations. Terminal flight
status is not evidence that pilots actually flew together.

The text bounds and exact required fields were approved with this document. Airport format checks do not verify that
an airport exists. Conversion of ambiguous/nonexistent user-entered local times
belongs to VOLO-175; this schema accepts an unambiguous instant and validates
its display zone/date relationship.

## Access and mutation boundary

Enable RLS and explicit least-privilege grants in the same migration that creates
the tables. An authenticated active member can read NETWORK flights; PRIVATE
reads require being the active owner or selected active recipient. Administrators
have no extra ordinary read access. Disabled and unadmitted identities cannot read
either mode, including with an existing JWT.

Owners can read their recipient list; selected recipients can read only their
own eligibility. Use a narrow, non-exposed private-schema predicate with a fixed
search path if necessary to avoid recursive flight/recipient RLS. Do not reuse
the directory-specific helper as a generic flight authorization function.

Revoke direct member insert/update/delete privileges. Future guarded posting and
recipient operations will establish write authorization and transactional mutation
interfaces. Initial privileged persistence access does not authorize application
use of a blanket secret client. Ownership and structural constraints still apply
to privileged writes.

VOLO-172 cancellation, conversation closure, history and locking requirements
remain mandatory when request/conversation and recipient mutations are introduced.
This migration neither exposes removal nor builds empty future lifecycle tables.
VOLO-174 reviews/refines these initial read policies rather than introducing
security after tables become exposed.

## Indexes and alternatives

Add stable upcoming-order indexes using departure_at and id, including an owner
index and NETWORK/PRIVATE query support. Add reverse recipient lookup by user_id
and flight_id; the composite primary key already supports flight audience lookup.
Keep indexes tied to the specified access patterns rather than speculative search.

Recommended: implement the VOLO-172 visibility predicate immediately, with writes
closed. Denying all reads would be safe but postpone useful policy verification;
adding write RPCs now would extend into posting and recipient lifecycle tickets.

## Focused verification and handoff

Reuse existing rolled-back pgTAP membership fixtures and local Supabase tooling.
Cover required fields, positive capacity, bounded text, airport normalization,
same-airport flights, valid/invalid zones, local dates across timezone/DST/date
boundaries, immutable owner, uniqueness and foreign-key deletion restrictions.
Cover NETWORK/PRIVATE role isolation, recipient-list privacy, current membership
revocation and direct-write denial, including spoofed metadata.

Generate types through the existing local CLI introspection script and check drift.
Update the existing migration-history allowlist used by upgrade verification.
Verify upgrade preserves existing Auth/membership/profile records with owned local
resources; do not create another test harness or run hosted write fixtures.

Read before design: VOLO-173, VOLO-45, VOLO-13, the VOLO-172 contract, existing
membership/profile/directory migrations and the installed Next.js data-security
guide. Existing application code has no flight flow. Application tests/full suite
are not necessary for this design document; SQL behavior tests follow implementation.

## Review decisions

The user approved the exact fields, lifecycle vocabulary, text limits, restrictive
deletion and closed member-write boundary above. Wider lifecycle
choices (accepted withdrawal, material edits, reactivation and general retention)
remain outside this ticket and are not silently decided here.
