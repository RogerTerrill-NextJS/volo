# Account deletion and retention — VOLO-226

This is the execution contract for [VOLO-227](https://outsidethecockpit.atlassian.net/browse/VOLO-227), the implementation step of [VOLO-91](https://outsidethecockpit.atlassian.net/browse/VOLO-91). It adds no deletion endpoint, migration or hosted operation. Reviewed against main `4c39804`, after VOLO-225.

## Approved policy and implementation boundary

Roger selected these policies in this chat on 2026-10-26:

| Decision | Approved outcome |
| --- | --- |
| Initiation/execution | A verified deletion request followed by founder-admin execution. No immediate self-service destructive action. |
| Shared history | Retain shared flight/request/message history for the other authorized participant under **Deleted pilot**. Remove the departing pilot's personal profile/photos and login access separately. |
| Retention | **60 days** for deletion-related audit, report and invitation records, and backups. No indefinite default. |

The ticket referred to an earlier VOLO-13 decision, but its current description still listed this as unresolved. These chat decisions supply the missing policy; they are not evidence of an earlier joint founder approval. The implementation recommendations below are the builder's design, not additional quoted founder decisions.

Use `verified_at` (server time when ownership verification and the deletion request are recorded) as the retention anchor; `purge_due_at = verified_at + 60 days`, using UTC instants. This explicit anchor is a design interpretation of the approved 60 days. An operator delay or retry does not restart it. Shared participant history has the separately approved retained-history treatment; the 60 days does not authorize wiping another pilot's conversations or flights.

A retention limit is a delivery requirement, not a statement of legal compliance or existing provider capability. A backup taken near day 60 can still contain retained audit/report/invitation data: configuring a generic 60-day snapshot lifetime alone does not prove that a subject’s data is gone 60 days after verification. The executor must establish an achievable combined live-data/snapshot schedule or obtain an explicit revised policy before enabling that promise. VOLO-227 must establish how retained snapshots/provider records expire before a hosted deletion workflow can promise completion.

## Existing constraints the implementation must preserve

- `memberships.user_id` and `profiles.user_id` restrict deletion of `auth.users`. Flights, requests, conversations, messages, reports, notifications and admin/moderation audits further restrict deletion of referenced members/records. A dashboard **Delete user** call cannot be assumed to work; replacing these with cascading deletes would destroy shared history.
- Invitation snapshots and send attempts directly reference Auth subjects in several roles: invited account, verified account, inviter, revoker and send requester. Their status/evidence constraints require coherent transitions. Nulling a referenced field or deleting whole rows blindly can invalidate live invitations or another pilot's admission evidence.
- Request/conversation identities and messages are immutable. Closure preserves the existing owner's/requester's authorized history; an admin role alone grants no general private-message access. SQL/schema changes for erasure must be narrow, reviewed retention operations, not new ordinary member update grants.
- `admin_disable_member` immediately removes protected membership access but retains Auth and all data. It prohibits self-disable. It is not account deletion and does not cancel every active flight/request or erase photos.
- Flight lifecycle operations serialize on the flight before requests/conversations and fence participant membership. Photo operations use profile → membership → photo-object locks. Do not introduce a long transaction holding member locks while acquiring flight/profile locks in the opposite direction.
- `profile_photo_objects` restricts profile deletion; its cleanup claims/acknowledgements need the profile row. Source uploads and finalized objects live in separate private buckets. Removing database rows does not remove stored bytes.

## Entry, authority and operator review

1. Provide a request path through the existing private support process. A signed-in request derives the subject from verified server identity, never a form-supplied email/UUID. A support request from an inaccessible/disabled account requires separately verified ownership before recording `verified_at`; an email string alone is insufficient. Do not invent a support address, response-time promise or send mail in this ticket.
2. Record the subject, verified request reference, verifying operator, fixed request ID, `verified_at`, `purge_due_at`, policy version and bounded phase/results in a restricted durable deletion record. Store no password, provider token, message body or unnecessary support transcript. Do not repurpose the immutable report table as a deletion queue.
3. A current active administrator reviews a bounded impact summary: target identity, own-flight/request/conversation counts, owned Storage work and retention obligations. The preview must not export other pilots' private records or message bodies. Require explicit target confirmation and a recorded request reference. Recheck administrator role/status and request ownership at each destructive database entry point; JWT metadata is not authority.
4. Reject self-execution and last-active-admin deletion through normal operator controls; another authorized administrator must execute. If no other administrator exists, use a separately approved access-recovery/admin-provisioning procedure first. An admin may request their own deletion but cannot silently remove the project's remaining operator.
5. Founder execution and hosted destructive work remain separately authorized operations. This document and its merge authorize no real account deletion, Storage purge, email or backup settings change.

## Record treatment

| Data | Immediate execution phase | At the 60-day boundary |
| --- | --- | --- |
| Membership/access | Disable permanently for deletion; retain an opaque tombstone key for shared references. No admission/reactivation from an old session or retained invitation. | Remove personal disable/reason/request metadata as approved; retain only the structural tombstone needed by retained shared history. |
| Profile | Remove directory/profile exposure and personal fields; show **Deleted pilot** only in authorized retained history. | Personal profile data must already be gone; no residual profile export. |
| Photos | Detach current photo, retire all target-owned reservations, delete both upload and final objects with acknowledged retries before deleting the parent profile. | No target photo bytes or identifiable cleanup payload may remain; overdue work is a failure, not an extended deadline. |
| Owned flights | Cancel all open posts, including elapsed open posts, and cancel their pending/accepted requests; close sending. Preserve terminal/shared flight history and its existing visibility limits. | Retained shared facts remain. Avoid new identity snapshots; free-text notes can contain personal data and are not anonymous. |
| Requests on others' flights | Withdraw pending/accepted requests, release accepted capacity and close related conversations; preserve terminal request history and other pilots' flights. | Retain authorized shared history/opaque linkage, not a live request or reusable account. |
| Conversations/messages | Keep shared history for the remaining authorized active participant; close future sends. Deleted sender displays **Deleted pilot**, with no profile/photo link. | Do not purge another pilot's messages or approved shared history. Retained message/note/introductory text can still identify people; deletion notice must disclose this exception accurately. |
| Notifications | Remove the target recipient's notifications; preserve other recipients' references only while they remain permitted. Links still reauthorize targets. | Minimize any departing-user identity exposure; retention grants no new target access. |
| Reports | Keep deletion-related reporter/target evidence restricted to authorized administrators during retention; disabled/deleted requester loses normal reads. Do not broaden message investigation access. | Purge target-subject report reasons/personal references according to the reviewed retention operation. Reports about another pilot and evidence required for that pilot must not be deleted wholesale merely because the departing person is referenced; minimize that person's identity instead. |
| Admin/moderation/deletion audit | Retain minimal execution evidence and unrelated targets' continuing evidence with restricted access. | Purge the departing subject's deletion-related personal reasons/identity references. Preserve only necessary structural facts for other users' records; ordinary users still cannot edit audits. |
| Invitations/send/setup/recovery | Revoke or retire target admission/setup/recovery authority; stop pending sends/reconciliation from restoring access. Retain required restricted evidence for up to 60 days. | Purge/minimize target email, subject/provider references and deletion-related evidence while keeping other recipients' active invitations valid. Do not delete invitations to other pilots wholesale because the departing user invited them. |
| Auth | Deny membership access before external Auth removal, revoke sessions/credentials through the supported privileged operation, and verify login/recovery/setup cannot regain admission. | No live login identity or target personal Auth data may remain merely to satisfy an old application FK. |
| Backups/logs/provider records | Record each relevant provider's actual retention and restore behavior, including Storage limitations. Do not copy erased material into new exports or logs. | Target personal data in retained backups/logs/provider records must age out within 60 days. If provider settings cannot meet this, stop release of the deletion promise and resolve the capability/policy conflict explicitly. |

“Deleted pilot” plus retained UUIDs/free text is **pseudonymized retained history**, not proof of anonymization or complete erasure. Keep existing audience and authorization checks. A remaining participant must not recover an otherwise hidden/private flight's details from a tombstone, audit, notification or report reference.

## Executable sequence for VOLO-227

Implement each phase with a durable receipt and bounded retries. Never claim a cross-service transaction across Postgres, Auth and Storage.

1. **Prepare the schema and proof locally.** Add a narrowly authorized deletion lifecycle/receipt and tombstone marker. Specify the exact Auth-reference migration before enabling the executor. Evaluate supported Auth soft deletion against local provider behavior versus hard deletion with detached structural identity; either must remove login/personal identity and preserve shared integrity. Soft deletion must not be described as physical row removal. Do not use a global synthetic Auth user, cascade shared rows, disable triggers, or leave all old Auth FKs permanently blocking cleanup. VOLO-227 must select and prove the concrete approach before its implementation review can pass.
2. **Verify/request and fence access.** Record the immutable request/clock, then atomically mark deletion pending and disable the target membership. Commit this access fence before taking flight/profile locks. Concurrent writes that committed before the fence become part of the impact inventory; later guarded mutations must deny the disabled target. Re-read inventory from authoritative tables, not the earlier UI counts. Signout alone is not an access fence: existing JWTs can remain valid. If an actor becomes disabled/demoted, deny new database phase authorization; retain pending state for an authorized successor.
3. **Close active collaboration in bounded batches.** Enumerate affected flights in stable order and use existing flight → request → conversation locking and state rules. Cancel target-owned open flights, withdraw target requests on others' flights, close all affected sends and confirm accepted capacity is released exactly once. The current requester-only withdrawal API cannot be called by an admin pretending to be the requester; add a deletion-only authorized transition that reuses its rules. Finished/cancelled flights and terminal requests stay terminal. Disabled membership blocks sends during partial cleanup; temporary capacity reservation is a pending phase until the batch completes.
4. **Retire identity and photos.** Under the established photo lock order, clear the profile photo reference and mark all owned lifecycle states for cleanup without allowing an in-flight finalize to reattach. Reuse [cleanupProfilePhotos](../lib/profiles/photo-cleanup.ts), owner-scoped in bounded batches with its lease/ack protocol. Existing cleanup eligibility alone is insufficient for unexpired pending/processing/ready reservations or a current attached photo: the deletion transition must explicitly retire them. Confirm both bucket objects absent and no owned/leased work remains before removing photo lifecycle/profile rows. Inventory unexpected owner-scoped Storage objects and handle them through the same authorized cleanup; never delete a shared bucket or another owner's prefix. Cleanup cannot rely on a client that has just lost membership.
5. **Retire auth/invitation authority.** Stop live admission/resend/setup/recovery operations for the target; invalidate finite transport/setup authority and prevent stale send outcomes or existing redeemed evidence from readmitting the tombstone. Preserve inviter/revoker/operator references needed by other users under the reviewed migration. Execute Auth cleanup server-side only after the application/Storage dependency checks succeed. Privileged clients are restricted to the verified subject and operation; do not expose their credentials or arbitrary admin-user deletion to the browser. Read back ambiguous Auth outcomes before retrying or marking the phase complete.
6. **Verify immediate completion.** Existing sessions, login, recovery/setup and direct/RPC/Storage/Realtime access for the target must deny; no open target flight/active request or writable target thread remains; profile/photos are unavailable. The other participant still has only their authorized retained history with **Deleted pilot**, and can continue using unrelated records. Show pending/retry status for failed external work; do not call a disabled-but-still-identifiable Auth account deleted. Separate immediate account removal status from `retention_pending`/retention-purge completion.
7. **Enforce the deadline.** Use the original UTC `purge_due_at`, not the final retry date. Provide a bounded subject-scoped purge/reconciliation job and overdue visibility; no silent rolling extension. At day 60, erase/minimize the approved personal audit/report/invitation/deletion payloads, including temporary receipts/logs and any stored subject/email mapping not required by the explicitly retained shared history. Existing immutability/FK constraints require reviewed narrow retention migrations and tests; no new unrestricted client DELETE grant. Keep a nonidentifying completion count/policy-version proof if needed, not another permanent personal archive.
8. **Verify backups/restores separately.** Inventory configured database/Auth/Storage/log/email-provider retention, actual snapshot age and access. Document provider evidence for the 60-day limit; a database backup does not necessarily include Storage bytes. Restore only into an isolated, access-denied environment, reapply outstanding deletion/purge decisions before reopening access, and never restore expired target personal data into production. A deletion suppression record itself must follow the 60-day policy; backups requiring an older identifying suppression list are a policy/capability conflict to resolve, not an indefinite exception. Hosted restore/retention changes require their own authorized operation.

## Failure handling and required evidence

No failure reactivates membership or rolls back already completed external erasure. Reuse the request ID/subject/phase receipt after timeouts; no new deletion job for every retry. A failure is visible as pending with bounded diagnostics and no tokens, message bodies, photos or other pilots' details. Recover by reading the authoritative phase result, never by rerunning unscoped Auth/Storage/SQL commands.

VOLO-227 must reuse existing owned local fixtures and add only the deletion-specific behavior coverage:

- Verified owner/admin authorization, forged subject/metadata, disabled/demoted operator, self-execution/last-admin denial and idempotent/ambiguous receipt handling.
- Cancellation/withdrawal versus acceptance/send/edit races; accepted capacity released once; all open/elapsed states accounted for; no post-fence writes or stale invitation redemption can reactivate the subject.
- Actual two-user history after profile/Auth cleanup, missing-profile fallback labels, unrelated/admin message denial, PRIVATE/hidden visibility, notification links and no cross-user erasure.
- Photo current/unexpired/in-flight/leased/orphan states, both buckets, failed deletion/ack and resumed cleanup without deleting parent rows prematurely.
- Concrete Auth/FK strategy proved against local Auth, all incoming subject references accounted for, stale sessions and current RLS/Storage/Realtime boundaries denied.
- UTC 60-day boundary and retries not resetting the clock; narrow retention purge with immutable constraints, another recipient's live invitation/audit evidence surviving and no personal data in completion logs.
- Provider retention/backup/restore proof recorded separately from unit/local assertions. Do not claim production erasure from a successful test, merge or preview.

## VOLO-227 implementation handoff

The implementation selects supported irreversible Auth soft deletion, proved with owned local Auth accounts, preserving the structural UUID rather than cascading shared data. The founder [operator runbook](account-deletion-operations.md) provides an authorized read-only impact preview, explicit target-confirmed begin and bounded resumable steps. New execution remains default-off until actual 60-day provider/backup evidence is recorded by a separately authorized operation. Database retention uses 1,440 elapsed hours (60 UTC days), independent of a caller’s daylight-saving timezone.

Retention minimizes report reason text while preserving reference evidence about other pilots. After a departing pilot’s deadline, new reports about their retained targets use the same canonical placeholder before receipt comparisons, preventing expired personal reason payload from being recreated. The form discloses this reference-only behavior. Shared history remains pseudonymous and subject to existing authorization; provider expiration and production erasure are not inferred from local checks.
